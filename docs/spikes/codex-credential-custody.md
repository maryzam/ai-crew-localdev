# Codex credential custody

An isolated Codex home used a custom Responses model provider whose `env_key` supplied a random placeholder and whose base URL pointed to a local host proxy. The proxy accepted only that placeholder, replaced it with the access token from the host's native ChatGPT login cache, added the host account ID, and forwarded the genuine Codex CLI request to the ChatGPT Codex backend. The proxy did not print or persist model request content or credentials.

One prompt completed with HTTP 200 on each installed Codex CLI version, 0.162.1 and 0.163.0. Each CLI sent one `/backend-api/codex/responses` request with the placeholder. Scanning the isolated Codex home after each run found neither the host access token nor the host refresh token. A direct backend request using a random placeholder returned HTTP 401.

The host Codex app-server's documented `account/read` request with `refreshToken: true` rotated both access and refresh tokens in the host login cache. A later placeholder-proxy prompt completed with HTTP 200 on 0.163.0 using the refreshed host state. These checks used genuine tokens issued by native ChatGPT sign-in; the placeholders were random values, not fabricated OAuth tokens.

[`internal/modelproxy`](../../internal/modelproxy) enforces this model boundary. The Codex handler accepts only `/backend-api/codex/models` and `/backend-api/codex/responses`, validates the run placeholder, supplies the host account ID, and writes evidence before forwarding. A failed evidence write latches the proxy closed. The host credential source requires an owner-only native `auth.json`, reads its access-token expiry, and uses the native Codex app-server to refresh before expiry or after a provider response that explicitly identifies an invalid token. Parallel requests share one refresh; a disconnected request does not stop it, and a late rejection of an old token cannot invalidate a newer token. Refresh succeeds when both tokens have changed for the same account and the new access token has more than one minute of validity, even if the native process must be stopped at its deadline. A partial rotation closes the source. A failed proactive refresh leaves an unrejected token available until ten seconds before its expiry, with at most one attempt per minute and three per hour; a rejected or expired token fails closed during backoff. A streaming redactor prevents an upstream response from echoing the host access token into the container.

After `ai login codex` publishes the dedicated broker login and the pinned refresh binary, `AI_CREW_CODEX_VERSIONS="0.162.1 0.163.0" make codex-proxy-compat` resolves the current published generation and runs the genuine CLIs in rootless Podman with `--network none`, a mounted run socket, and an isolated Codex home. The gate forces a refresh of the dedicated broker login, checks that both tokens rotate, and requires model answers, a tool-created file, session resume, cross-version resume when two versions are selected, rejection of a copied placeholder, absence of host tokens from container-visible files and evidence, and prompt model failure after broker shutdown. It refuses the operator's normal Codex login path, so compatibility runs cannot rotate that login.

Native refresh uses a SHA-256-pinned ELF copy in a private broker directory outside the operator's updating Codex home. It opens the executable without symlink traversal and executes its verified file descriptor with both `HOME` and `CODEX_HOME` set to the dedicated broker auth directory. It starts the app-server in its own process group; the 20-second deadline kills that group and closes the stdout pipe, bounding the drain even when a child inherited stdout. `WaitDelay` is set to two seconds for process and pipe cleanup. Requested, rotated, failed, deferred, refused, and explicit invalidation outcomes are recorded, including elapsed refresh time and whether a complete rotation outlived the native process; unavailable evidence blocks credential release. The broker auth directory and file must be owner-only. The shared proxy core applies the same route, credential-header, audit, response-redaction, and evidence-latching rules to Claude and Codex. Focused checks cover concurrent requests, confirmed token rejection, process timeout after complete rotation, inherited stdout, proactive refresh failure while a token remains valid, pinning, audit failure, credential smuggling, and response credential echoes.

`ai login codex` forces native file credential storage and publishes each login as a new owner-only credential generation. This package is frozen and `ai up` is not wired to it; it is extracted into `internal/product` before `ai up` consumes it, and the extracted refresh must publish each rotation as a new generation rather than rewriting a published one, because a rewritten file no longer matches its custody record. The frozen proxy also refuses refresh binaries larger than 200 MiB, while the pinned Codex 0.163.0 binary is about 283 MiB, so `make codex-proxy-compat` cannot pass until that extraction verifies the binary with a streamed hash; the gate is the acceptance check for the extraction. Arbitrary future CLI upgrades and optional Codex endpoints still need their compatibility checks.

[OpenAI's authentication documentation](https://learn.chatgpt.com/docs/auth) describes native ChatGPT login caching and automatic refresh. [The gateway documentation](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway) supports forwarding genuine Codex requests through a gateway, but its documented configuration sends the real ChatGPT token from the CLI. The exact host-side substitution tested here is not explicitly documented there. [Sign in with ChatGPT for open-source apps](https://developers.openai.com/siwc/token-sharing-open-source) provides a separately registered application flow. The spike established technical compatibility, not an express terms approval. The project owner decided to support the host-held proxy for genuine Codex CLI model requests unless OpenAI clearly restricts that use. The proxy does not expose the subscription credential to the task container.
