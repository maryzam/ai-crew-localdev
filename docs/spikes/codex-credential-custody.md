# Codex credential custody

An isolated Codex home used a custom Responses model provider whose `env_key` supplied a random placeholder and whose base URL pointed to a local host proxy. The proxy accepted only that placeholder, replaced it with the access token from the host's native ChatGPT login cache, added the host account ID, and forwarded the genuine Codex CLI request to the ChatGPT Codex backend. The proxy did not print or persist model request content or credentials.

One prompt completed with HTTP 200 on each installed Codex CLI version, 0.162.1 and 0.163.0. Each CLI sent one `/backend-api/codex/responses` request with the placeholder. Scanning the isolated Codex home after each run found neither the host access token nor the host refresh token. A direct backend request using a random placeholder returned HTTP 401.

The host Codex app-server's documented `account/read` request with `refreshToken: true` rotated both access and refresh tokens in the host login cache. A later placeholder-proxy prompt completed with HTTP 200 on 0.163.0 using the refreshed host state. These checks used genuine tokens issued by native ChatGPT sign-in; the placeholders were random values, not fabricated OAuth tokens.

[`internal/modelproxy`](../../internal/modelproxy) now enforces this model boundary. The Codex handler accepts only `/backend-api/codex/models` and `/backend-api/codex/responses`, validates the run placeholder, supplies the host account ID, and writes evidence before forwarding. A failed evidence write latches the proxy closed. The host credential source requires an owner-only native `auth.json`, reads its access-token expiry, and uses the native Codex app-server to refresh before expiry or after an upstream 401. Parallel requests share one refresh; a disconnected request does not stop it, and a late 401 for an old token cannot invalidate a newer token. Refresh succeeds only after the native process exits and both tokens have changed on disk. Failure to read or refresh the host login refuses the model request. A streaming redactor prevents an upstream response from echoing the host access token into the container.

`AI_CREW_CODEX_AUTH_FILE=<broker-only auth.json> AI_CREW_CODEX_BINARY_SHA256=<reviewed host binary digest> AI_CREW_CODEX_VERSIONS="0.162.1 0.163.0" make codex-proxy-compat` runs the genuine CLIs in rootless Podman with `--network none`, a mounted run socket, and one persistent isolated Codex home. The check deliberately refreshes the dedicated broker login once, verifies that both tokens rotate, then verifies live model responses across versions, provider rejection of the copied placeholder, and absence of host tokens from the agent home and evidence. It refuses the operator's normal Codex login path, so compatibility runs cannot rotate that login. A broker login must be created separately through native Codex sign-in before running this check.

Native refresh uses a SHA-256-pinned ELF copy in a private broker directory outside the operator's updating Codex home. It opens the executable without symlink traversal and executes its verified file descriptor with both `HOME` and `CODEX_HOME` set to the dedicated broker auth directory. It has a 20-second process deadline plus a two-second pipe wait, at most one attempt per minute and three per hour. Requested, rotated, failed, and budget-refused outcomes are recorded; unavailable evidence blocks credential release. The broker auth directory and file must be owner-only. The shared proxy core applies the same route, credential-header, audit, response-redaction, and evidence-latching rules to Claude and Codex. Focused checks cover concurrent requests, 401 recovery, native refresh completion, token rotation, pinning, audit failure, credential smuggling, and response credential echoes.

`ai login codex` and `ai up` have not yet been wired to this package. The login flow must choose native file credential storage in a broker-only volume; arbitrary future CLI upgrades and optional Codex endpoints still need their compatibility checks.

[OpenAI's authentication documentation](https://learn.chatgpt.com/docs/auth) describes native ChatGPT login caching and automatic refresh. [The gateway documentation](https://learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway) supports forwarding genuine Codex requests through a gateway, but its documented configuration sends the real ChatGPT token from the CLI. The exact host-side substitution tested here is not explicitly documented there. [Sign in with ChatGPT for open-source apps](https://developers.openai.com/siwc/token-sharing-open-source) provides a separately registered application flow. The spike established technical compatibility, not an express terms approval. The project owner decided to support the host-held proxy for genuine Codex CLI model requests unless OpenAI clearly restricts that use. The proxy does not expose the subscription credential to the task container.
